# C++ hybrid decoder: amplitude-scaled LLRs, min-sum and OSD-2

The C++ receiver was measured with the hybrid chain that was proposed for weak
signals: per-carrier LLR scaling from the channel estimate, a short min-sum
belief-propagation pass, then order-2 ordered-statistics reprocessing (OSD-2)
with the block CRC as the acceptance test. The point of the exercise was to see
whether any of it moves the sensitivity floor, not to assume it does.

## What was added

* **Per-carrier LLR variance.** After equalisation, a cell's noise variance is
  `sigma^2 / |H|^2`, so a faded carrier no longer carries the same weight as a
  strong one. The receiver already estimated one scalar variance from the pilot
  curvature; it now keeps the per-cell value as well, for the header and the
  payload. `--llr flat` restores the old scalar behaviour for the payload.
* **Normalised min-sum.** `--decoder ms --iters N` uses the two-smallest-
  magnitude check-node update with a 0.75 weight instead of the tanh rule.
* **OSD-2.** `--decoder sposd` (sum-product, then OSD) or `--decoder msosd`
  (min-sum, then OSD) orders the bits by reliability, inverts the parity block
  over GF(2), and re-encodes from the k most reliable columns. It flips pairs
  among the 10 least reliable information bits and accepts a candidate only when
  its syndrome is clean and the block CRC passes.
* **AWGN bench.** `bench --mcs N --snr DB --frames F [--fading]` builds frames,
  adds noise referred to the signal's occupied bandwidth (117 carriers,
  2 742 Hz, the same convention as `halcyon/channel.py`), and reports block and
  frame error rates on the C++ receive path.

Nothing was changed in the frame format, the LDPC matrices or the interleaver.
The Python modem is untouched.

## AWGN, MCS 4 (QPSK 1/2), 40 blocks per point

Block error rate after CRC-16; 10 frames x 4 blocks.

| S/N (2.7 kHz) | sum-product 40 | min-sum 10 | min-sum 10 + OSD-2 | sum-product 40 + OSD-2 |
|--------------:|---------------:|-----------:|-------------------:|-----------------------:|
| 2 dB | **45.0 %** | 95.0 % | 95.0 % | 45.0 % |
| 3 dB | **0.0 %** | 15.0 % | 15.0 % | 0.0 % |
| 4 dB | 0.0 % | 0.0 % | 0.0 % | 0.0 % |
| 5 dB | 0.0 % | 0.0 % | 0.0 % | 0.0 % |

At 2 dB with 40 frames (156 blocks) sum-product and sum-product + OSD-2 both
reported 43.6 % (68 failed blocks): OSD found no CRC-valid candidate in any of
them. Raising min-sum to 40 iterations does not close the gap either: 62.5 % at
2 dB and 10.0 % at 3 dB, against 43.8 % and 0.0 % for sum-product.

The flat-versus-channel LLR comparison on AWGN is small but not zero: at 2 dB,
20 frames, channel scaling gives 43.8 % against 55.0 % flat. The pilot-noise
estimate is not perfectly flat across carriers even without fading, so keeping
the per-cell value helps slightly.

## Frequency-selective channel, MCS 4

A two-tap channel: direct path plus a 0.7 echo 8 samples (667 us) behind it, so
the coherence bandwidth is about 1.5 kHz across a 2.7 kHz signal. 20 frames x 4
blocks per point, sum-product at 40 iterations. The header is decoded with the
same per-carrier LLRs, so all 80 blocks are observed; with the header still on
the old scalar variance, one frame per run lost its header. A separate 6 dB run
also decoded 80/80 blocks with no frame errors.

| S/N (2.7 kHz) | channel LLR (default) | flat LLR (old path) |
|--------------:|----------------------:|--------------------:|
| 8 dB | **0.0 %** (0/80) | 25.0 % (20/80) |
| 10 dB | **0.0 %** (0/80) | 7.5 % (6/80) |
| 12 dB | **0.0 %** (0/80) | 2.5 % (2/80) |

Frame error rate over the same runs: 0 % channel against 55 % flat at 8 dB,
0 % against 25 % at 10 dB, and 0 % against 10 % at 12 dB. The flat payload path
needs more than 12 dB to reach the block reliability the scaled path already has
at 8 dB, so the weighting is worth roughly 4 dB or more on this channel, and
scaling the header as well removes the remaining header losses.

## Before/after on identical captures

The pre-change receiver was built from commit `1612227` in a separate worktree.
Both C++ binaries then decoded the same captures, generated by the Python modem
at MCS 4 with 4 blocks per frame and 20 frames per point. Values are header OK /
fully decoded frames / decoded blocks, as percentages of 20 frames and the 80
expected blocks; a lost header counts as failed blocks. The Python modem is
shown unchanged because its receive path was not modified.

| Channel | S/N | Python (unchanged) | Before `1612227` | After (default) |
|---|---:|---:|---:|---:|
| AWGN | 2 dB | 90 / 5 / 42 % | 90 / 5 / 42 % | **100 / 15 / 65 %** |
| AWGN | 3 dB | 95 / 85 / 92 % | 95 / 85 / 92 % | **100 / 90 / 98 %** |
| 667 us echo | 6 dB | 45 / 0 / 5 % | 80 / 0 / 12 % | **100 / 100 / 100 %** |
| 667 us echo | 8 dB | 50 / 25 / 41 % | 100 / 40 / 74 % | **100 / 100 / 100 %** |

Mean C++ receive time per frame over the same runs was 84-128 ms before and
71-107 ms after, so the extra per-cell LLR work did not cost speed. The Python
modem still uses its original scalar variance; it matches the before column on
AWGN and trails it under fading.


## Decision

* **Keep per-carrier LLR scaling as the default for header and payload.** It is
  the one part of the proposed chain that produced a measured sensitivity gain,
  and it costs one division per cell.
* **Keep 40-iteration sum-product as the payload decoder.** Ten min-sum
  iterations starve belief propagation: 95 % block errors against 45 % at 2 dB.
  Even at 40 iterations min-sum trails sum-product here.
* **Leave OSD-2 off by default.** It adds a GF(2) inversion and up to 55
  re-encodes per failed block, and it recovered none of 68 failed blocks at
  2 dB. The option remains for experiments on other rungs and channels.
* **No ALSA front end.** The C++ core still consumes float32 IQ from a file;
  there is no audio device layer in the repository, so the chain was measured
  from IQ onward. Adding ALSA would be a separate, hardware-dependent change.
* **No polar SCL.** The C++ air interface is LDPC-only; polar exists in the
  Python experiments but not in a C++ frame format. OSD is the ML-style
  reprocessing arm for the code that is actually transmitted.

Timing on this machine, including acquisition, is 70-115 ms per frame at these
levels; OSD adds 3-6 ms on the frames where it runs. All arithmetic is double
precision. AVX2 was not added: the measured problem was decode reliability, not
throughput, and the GF(2) OSD work does not vectorise the same way as LLR math.
